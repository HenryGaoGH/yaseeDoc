# 01｜测试背景与目的

## 1.1 测试背景

随着 Android 终端连接 BLE 设备数量增加，设备扫描、GATT 建连、服务发现、Notification 订阅及业务初始化等环节可能对整体 READY 时间产生影响。

本次专项验证围绕 Android BLE 多设备连接场景，评估连接链路性能及应用层对 READY 时间的控制能力。

考虑到自研 Android BLE SDK 主要是对 Android 原生 BLE API 的轻量封装，本次不再单独开展 SDK 与 Android 原生 API 的性能 A/B 对照测试，而是将重点放在 SDK 基础功能正确性、硬件性能差异、Android 终端差异、多设备并发能力及 3 秒 READY 可控性上。

## 1.2 核心验证目标

### 目标一：SDK 基础功能正确性

检查自研 Android BLE SDK 对原生 BluetoothGatt API 的封装和调用是否正确。

重点验证：

- BLE 扫描及设备发现。
- GATT 连接及状态回调。
- GATT 服务发现。
- Notification 订阅。
- 多设备连接状态管理。
- 异常处理及资源释放。

不再将 SDK 与 Android 原生 API 作为独立性能对照变量。

### 目标二：硬件性能对照

通过自研硬件与第三方硬件对照，分析不同硬件 BLE 实现及协议行为对连接性能的影响。

重点关注：

- BLE 广播性能。
- GATT 连接性能。
- 服务发现性能。
- Notification 订阅性能。
- 断开重连性能。

### 目标三：多 Android 终端兼容性

通过不同品牌、不同 Android 版本的手机进行测试，分析终端蓝牙芯片、驱动及系统蓝牙协议栈对连接性能的影响。

### 目标四：3 秒 READY 可控性

通过不同手机、不同 BLE 设备数量及不同无线环境下的测试，验证应用层能否稳定实现 3 秒 READY 目标。

## 1.3 验证原则

1. 不预设 SDK 或硬件存在问题。
2. 不混淆 BLE 协议差异与硬件性能差异。
3. SDK 作为原生 API 轻量封装，不进行重复的性能 A/B 对照。
4. 不使用未经验证的数据。
5. 所有结论必须有实际测试数据支撑。
6. 明确 3 秒 READY 目标所适用的终端、设备数量及无线环境边界。

## 4.1 验证目的

自研 Android BLE SDK 主要是对 Android 原生 BLE API 的轻量封装。

因此，本次不再单独开展 SDK 与 Android 原生 API 的性能对照测试。

本章节主要验证 SDK 是否正确调用 Android 原生 API，以及是否存在回调处理、状态管理、多设备资源管理等实现问题。

## 4.3 多设备状态管理检查

1. 每台设备是否独立维护连接状态及 GATT 实例。

# 08｜3 秒 READY 可控性分析

## 8.1 核心验证目标

验证在不同手机、不同 BLE 设备数量及不同无线环境下，应用层能否稳定保证所有目标设备在 3 秒内达到业务 READY 状态。

## 8.2 READY 时间定义

统一定义：

**READY 耗时 = 业务 READY 时间戳 - 测试起始时间戳**

测试起始时间应统一定义为应用层开始执行连接流程的时刻。

READY 必须满足：

1. GATT 连接成功。
2. 服务发现完成。
3. 必要 Notification 订阅成功。
4. 必要业务协议交互完成。
5. 应用层确认设备可以正常执行业务操作。

不能仅以 GATT 连接成功作为 READY。

对于多设备场景，建议以所有目标设备均达到 READY 的时间作为本轮整体 READY 时间，以避免单台设备达标掩盖其他设备超时的问题。

- Android 蓝牙协议栈内部调度。
- 手机蓝牙芯片及驱动行为。
- BLE 无线信道竞争。
- 外设响应速度。
- 系统资源调度。
- 外部无线干扰。

因此，是否能够保证 3 秒 READY，需要通过实际测试和目标环境边界定义进行验证。
